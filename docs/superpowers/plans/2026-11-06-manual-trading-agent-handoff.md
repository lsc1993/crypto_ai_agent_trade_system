# 实盘手动计划 Agent：跨模型开发交接

- 版本：1.1；日期：2026-11-06。
- 用途：新模型或新会话不依赖此前聊天记录即可定位范围、按批次实施并提交可复核证据。
- 当前状态：需求与设计已成文，实施计划/契约为 v1.1；T00–T19 尚未执行。本文件不表示环境、依赖或新功能已经通过验收。

## 1. 唯一目标与必读入口

目标是 **Agent 分析与辅助决策 → 确定性计算和风险/市场规则核验 → 用户审核 → 用户自行在交易所手动操作**。完整 Tool Calling、MCP、RAG、动态上下文、Token 治理、人机交互、Harness 和实盘手动计划均为核心；本期不做自动交易，也不实现尚未提供的 MACD/三重过滤/用户组合算法。监控默认关闭，调度与提醒留 D6 后续计划。

按顺序读取：

1. [根 AGENTS.md](../../../AGENTS.md)，按范围读取[后端](../../../backend/AGENTS.md)/[前端](../../../frontend/AGENTS.md)规则。
2. [需求 v2.0](../specs/2026-11-06-manual-trading-agent-requirements.md)：业务范围、FR、默认审核 AP、验收 AC。
3. [架构 v2.0](../specs/2026-11-06-manual-trading-agent-design.md)：职责、运行不变量 HN、恢复/预算/人工审核与风险边界。
4. [实施计划 v1.1](2026-11-06-manual-trading-agent-implementation.md)：T00–T19、文件、依赖、红绿验证与交付门槛。
5. [实施契约 v1.1](2026-11-06-manual-trading-agent-contracts.md)：C1–C10 的跨任务类型、接口、字段与技术选择。
6. [AI 维护](../../ai-maintenance.md)、[运行边界](../../operational-boundaries.md)、[质量验证](../../quality-verification.md)、[项目状态](../../project-status.md)：当前已实现行为与验证环境。

研究版 v1.x、早期架构和原始下载技术方案保留为背景，不替代当前 v2 目标；不要求执行者访问原始下载目录或取得之前聊天记录。特别是旧版排除资金/仓位规划的范围已经被 v2 替代。

现行 AGENTS.md 在对应任务实际修改前仍然有效。T00 先完成命名/规范和门禁路径迁移，T09/T11 才按计划开放受控工具循环；不能直接忽略旧规则，也不能因为旧规则而把目标缩回固定报告格式化流程。

## 2. 不依赖特定模型或个人技能

计划中的 Superpowers 技能名描述工作方法，不是生产依赖；执行客户端没有这些技能时，无需安装插件或复制个人缓存。执行等效流程即可：

- 一个执行上下文负责当前任务和其接口依赖，先写有意义的失败测试，再实现、聚焦验证、阶段完整验证及审查。
- 先读取本任务 Interfaces 与依赖任务的产出，不能凭当前局部上下文重新设计公共类型。
- 保留可关联的改动和验证记录，不用“模型说已完成”替代测试结果。
- 可使用可用子 Agent 时遵守仓库及用户的模型选择规则；没有此能力时可由单会话逐任务完成，不伪称进行了独立审查。
- 交付前独立审查关键资金、事务、权限和恢复代码；未审查时明确待审，不以生成模型自评充当独立审查。

不把编写计划的模型、应用运行时调用的 LLM、执行开发任务的模型绑定为同一个模型。开发执行者可更换；产品模型接口仍按计划记录 requested/returned model、能力与版本指纹。

### 用户指定的开发与审查分工

用户已指定：其他模型负责开发，以形成异构协作；每个模块完成后交回原设计与审查助手正式审查。完整启动提示词见[开发模型提示词](2026-11-06-manual-trading-agent-developer-prompt.md)。默认一个 Txx 任务为审查单元，用户明确组合多个任务时以该组合为单元。

开发端完成实现和自测后生成 `docs/superpowers/reviews/manual-agent/<任务ID>-review-request.md`，固定 base/tip、改动范围与验证证据，并进入 awaiting_review。用户把材料交回原助手审查；开发模型及其本地自动检查不得代替该正式结论。收到修复意见后修复、重验、提交新版本再审；当前版本通过且必需验证完成后才可放行下一审查单元。即使用户授权连续开发某阶段，也保留模块间此门槛，除非用户明确更改协作约定。

工程模块审查与产品的 AP-01 至 AP-07 审核互不授予权限；不因此增加生产运行状态或修改单 Agent 架构。

## 3. 实施前检查与正确顺序

1. 记录选定代码提交、分支、工作区差异及文档版本；以包含本交接文件的实际提交为文档基线。计划中的 `4534ee9` 是当时源码核对基线，不是要求回退到该提交。
2. 检查并保留已有未提交内容。文档编写时已有 20 个跟踪文件未提交，不允许打包提交、覆盖、清理或自行 stash 这些其他任务改动。隔离工作区从明确选定提交创建，需要的其他修复由原任务独立处理。
3. 按质量说明运行只读 doctor，记录 Python/Node/依赖、专用测试库、Docker 与浏览器前提。缺少条件不自动修改环境、业务配置或 `.env`；能独立推进的非阻塞工作可继续。
4. 默认从 T00 开始。T01 先建立公共类型，T02/T03 按迁移链接续；**T06 必须在 T05 定义 ExecutionContext/RunFence 等纯类型后执行**；T11 图只依赖本任务定义的 AnalysisArtifactStager 协议，生产产物实现到 T14；T15 先扩展 AgentCatalogApi，T16 补齐三个适配器后才扩展完整 AgentWorkbenchApi。
5. T12 可按计划在 T01/T03 后提前做纯计算；其他并行仅限已明确稳定的依赖和互不冲突的文件。共享迁移序号、装配文件和公共契约由同一协调者合并，不允许多个执行者各建不相容版本。

进入每个任务时复核依赖是否真正验证通过，不能只读前一个模型的完成总结。计划中模型/MCP/SQL/浏览器测试的范围不同，不互相替代。

## 4. 每任务交付与跨会话接续

建议执行者从首个任务起维护 `docs/superpowers/execution/2026-11-06-manual-agent-progress.md`，只保存安全摘要。该文件由执行任务创建，本轮不预填完成记录。

每任务至少记录：

| 项目 | 必须写明 |
| --- | --- |
| 身份 | 任务 ID、FR/AC/HN、开始/结束时间、基线与提交 hash |
| 改动 | 实际文件、公共接口与迁移变化、消费/产出契约版本 |
| 测试 | 执行目录、完整命令、退出码、实际通过/失败/跳过/收集数、证据路径 |
| 审查 | 审查范围、审查者/独立上下文、问题及修复结果；没有则待审 |
| 遗留 | 未验证项、阻塞条件、下一步和是否影响依赖任务 |

任务状态区分 pending/running/implemented/verified/blocked。写出实现但缺少 SQL 验证只能记 implemented，不能记 verified；复选框只在对应步骤真实完成后勾选。不能批量预勾，也不能用 quick 替代要求的 full。

另设开发交接记录字段 review_status（awaiting_review/changes_requested/approved）及 reviewed_tip，不修改产品任务状态机。verified 只表达验证，不等于正式审查 approved；结论必须由用户传回原审查助手对准确版本的审查结果，不由开发模型自行填写。

会话/模型切换时，新执行者先读此进度文件和真实 git diff/log，核对已有证据，再选第一个依赖已满足的任务。发现摘要与代码/测试不一致时以核实结果修正记录，不重做已经验证的任务，也不无条件相信旧摘要。

`.tmp/` 原始产物通常不随 Git 传递，换机器时必须留下可复核的安全摘要和重现命令；不能把缺失的旧产物当本轮验证成功。进度文档不写个人工具路径、凭证、连接串、真实财务资料、模型原文或私有账户信息。

## 5. 哪些可自行处理，哪些必须说明

| 情况 | 处理原则 |
| --- | --- |
| 私有辅助函数、内部拆分、索引/类型实现、正常失败修复 | 在既定约束内自主处理，补有意义测试；不为这些常规选择重复询问用户 |
| 公共字段/错误码需细化、计划路径随源码漂移 | 先同步契约、消费者与验证；不改业务语义的技术细节可自行落实并记录，不能一端悄悄改名 |
| 已计划 SDK 无法与锁定依赖相容、迁移 head 变化 | 给出真实兼容/迁移证据，调整对应计划记录；不得隐式整体升级框架、改旧迁移或取消门禁 |
| 缺测试库/权限/浏览器 | 记录 blocked 和缺失条件，继续独立可做部分；不把跳过、零收集或未执行写为通过 |
| 真实模型额度未授权 | 完成离线工具和评估协议，真实质量保持 pending；不借用历史额度、默认配置或日常 full 触发付费请求 |
| 改核心目标、默认审核、资金权限、自动交易或新增外部服务 | 属于范围/授权变化，先说明具体差异与影响，按用户指令和变更规则处理；不能以“完整 Agent”自行扩权 |
| 当前任务已授权、常规实现可逆且约束明确 | 持续完成授权范围，不反复确认已对齐的手动实施、策略算法范围或默认规则 |

新增依赖和 schema 的预期影响已在计划登记，实际实施仍先核对并说明最终差异；这不授权部署、业务库迁移、访问私有账户或操作真实资金。没有任何运行中审批能绕过硬风险、数据完整性和产品不支持的阻断。

## 6. 必须分开报告的完成状态

| 状态层 | 证明 |
| --- | --- |
| 任务实现完成 | 当前任务代码、契约、注释和文档已落地；不是所有验证均通过的同义词 |
| 软件验收通过 | 聚焦、统一 full、要求的 SQL/故障/HTTP/MCP/浏览器检查有实际证据，关键不变量全部满足 |
| 真实模型质量通过 | 版本化场景、重复运行、完整分母、具名人工评分及独立复核满足设计门槛；未运行或未评分为 pending |
| 产品手动规划支持发布 | 现行规则来源和支持范围已核对，真实成本/保证金资料流程可用；单份计划仍需当前用户资料、确定性检查和审核 |
| 用户实际收益 | 具体策略、成本、样本和人工执行记录；本期框架测试不证明收益，user_reported 不等于独立核实 |

付费模型评估尚未获额度时，可以交付已验证的软件和待验收项，不能宣称完整实际模型质量已通过；产品规则未核对时不能宣称该产品可用于实盘。用户策略算法尚未提供时不能宣称已实现其组合或盈利能力。

开发使用合成资金资料和已审查方法文档即可启动。具体策略说明、用户知识及实际规划资金/风险/费率/保证金资料在后续接入或实际使用时提供，无须为了开始框架开发提交真实账户信息或完整知识库。
