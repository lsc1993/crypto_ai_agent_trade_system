# 回测响应小数精度对齐设计

## 目标

确保历史回测 API 的成功响应能被前端 `BacktestRunDetail` 与 `BacktestRunSummary` 合约解析，同时不改变回测引擎、风控决策、冻结 K 线或持久化审计数据。

## 已确认问题

回测引擎会产生超过 18 位小数的比率与汇总指标。后端原样序列化这些 `Decimal` 值；前端公共十进制字符串合约限制小数部分至多 18 位。因此 API 虽返回 201 或 200，前端 HTTP 传输层仍将响应视为无效，列表读取与创建回测均进入失败状态。

## 方案比较

1. 放宽前端小数合约：会让浏览器端接受超过数据库金额精度的数值，并扩大所有复用该合约的输入/输出范围。
2. 在回测引擎中提前量化：会改变内部计算、快照/指标存储与审计复算语义。
3. 仅在回测 API 响应边界量化：保留内部精度和持久化值，只使 UI 传输值符合现有公共合约。

采用方案 3。

## 设计

在 `app.api.routes.backtests` 定义仅供该路由响应模型使用的十进制序列化器。它使用 `ROUND_HALF_EVEN` 将值量化到 `Decimal("0.000000000000000001")`，并以固定小数格式序列化；计算时根据当前值的有效数字数设置足够高的本地 `Decimal` 精度，避免量化大金额或高精度比率时触发上下文精度异常。

所有回测响应中的金额、数量、风险参数与汇总指标都使用该响应类型。领域模型、回测引擎、JSONB 指标、冻结 K 线和审计事件保持原样。

## 验证

在 API 路由集成测试中构造包含超过 18 位小数的回测结果，验证创建、列表和详情响应中的相关字段均是最多 18 位小数的规范字符串，并保留半偶舍入结果。运行后端回测路由与引擎测试，以及前端 HTTP 客户端与页面测试、Ruff、Pyright 和前端类型检查。
